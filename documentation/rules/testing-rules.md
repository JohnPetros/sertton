# Testing Rules

This document defines the testing standards for `sertton-react-native-app`. The strategy must validate behavior at the appropriate layer, keeping tests fast and isolated whenever possible and reserving complete user journeys for E2E tests.

## 1. Testing strategy by layer

~~~text
                 Maestro E2E
              /              \
     HTTP/API integration    Widget/screen
              \              /
             Hooks, controllers and core
~~~

### Unit tests

Unit tests validate one isolated unit without network, database, or device dependencies:

- entities and pure functions from `core`;
- UI hooks;
- controllers;
- mappers and adapters;
- validation and transformation rules.

External dependencies must be replaced with controlled mocks or fakes.

### Widget and screen tests

Widget and screen tests validate rendered JSX, visual states, accessibility, and user interaction. The screen hook is mocked so the view test does not duplicate the hook's behavior coverage.

The hook must be tested separately with `renderHook`.

### HTTP integration tests

HTTP integration tests validate the composition of an Expo API Route, `ExpoRoute`, controller, and service. They should use `Request`/`Response` directly or make HTTP requests against the Expo server.

The service contract may be replaced when the goal is to test only the route and controller. When the goal is to validate Yampi integration, use the local server at `tests/mocks/yampi-mock` without mocking the UI hook.

### E2E tests with Maestro

Maestro flows represent complete functional journeys in the running or installed application. Although they may be informally called integration tests, they are technically E2E tests: they exercise the UI, navigation, Expo API, and Yampi mock server.

Maestro does not replace unit tests. It should cover critical journeys and detect composition problems between layers.

## 2. File organization

### Jest UI tests

Tests live close to the code under test, in a `tests` directory inside the widget:

~~~text
src/ui/<domain>/widgets/<widget>/
├── index.tsx
├── use-<widget>.ts
└── tests/
    ├── <widget>.test.tsx
    └── use-<widget>.test.tsx
~~~

Examples:

~~~text
src/ui/global/widgets/screens/home/tests/home-screen.test.tsx
src/ui/global/widgets/screens/home/tests/use-home-screen.test.tsx
src/ui/global/widgets/screens/home/product-card/tests/product-card.test.tsx
~~~

Internal widgets deserve their own test when they contain behavior, navigation, state, selection, effects, or relevant presentation rules. A purely structural component with no observable behavior does not require an independent test.

### Controller and API Route tests

Keep tests close to the layer under test:

~~~text
src/rest/controllers/<domain>/tests/<controller>.test.ts
src/app/api/<route>/tests/<route>.test.ts
~~~

When adding these tests, update `testMatch` in `jest.config.ts` so they are discovered by the default `npm test` command.

### Maestro tests

Functional flows live in `tests/screens`, grouped by screen:

~~~text
tests/
├── mocks/
│   └── yampi-mock/
└── screens/
    └── home/
        ├── home-content.yaml
        ├── home-newsletter.yaml
        ├── home-newsletter-success.yaml
        ├── home-search.yaml
        └── home-search-empty.yaml
~~~

The `.maestro` directory is not mandatory. This project uses `tests/screens` as its convention. Flow files must use the `.yaml` extension.

## 3. Naming

- Name files after the behavior under test: `home-screen.test.tsx`, `use-home-screen.test.tsx`.
- Use the module or component name in `describe`: `describe("useHomeScreen", ...)`.
- Write test cases in English, preferably starting with `should`: `it("should render the loading state", ...)`.
- Name mocks with the `Mock` suffix, never with the `mocked` prefix:

~~~ts
const useHomeScreenMock = jest.mocked(useHomeScreen)
const catalogServiceMock = mock<CatalogService>()
const routerMock = jest.mocked(router)
~~~

- The name should describe the mock's role, not its internal implementation.

## 4. Fakers

Use fakers for entities, DTOs, and responses with meaningful structure. This avoids repeated data and makes contract changes easier to maintain.

Core fakers live next to their entities:

~~~text
src/core/<domain>/entities/fakers/<entity>-faker.ts
~~~

Each faker must be a class with static methods. The customization argument is optional and must accept `Partial` of the entity:

~~~ts
export class ProductFaker {
  static fake(product?: Partial<Product>): Product {
    return {
      // default values generated by faker
      ...product,
    }
  }

  static fakeMany(count = 10, product?: Partial<Product>): Product[] {
    return Array.from({ length: count }, () => ProductFaker.fake(product))
  }
}
~~~

Customize only the data relevant to the scenario:

~~~ts
const product = ProductFaker.fake({
  name: "Arramate",
  skuCode: "SKU-1",
})
~~~

Do not use a faker to hide the state that matters to the test. The reader must be able to understand why the data makes the scenario pass.

Yampi mock server fakers belong in `tests/mocks/yampi-mock/fakers`. They represent the external Yampi format and must not be confused with core entity fakers.

## 5. Mocks and test doubles

### Main rule

Mock the boundary that the test is not intended to validate. Do not mock the unit under test.

### Core interfaces

Use `ts-jest-mocker` for core services and interfaces:

~~~ts
import { mock, type Mock } from "ts-jest-mocker"

let catalogServiceMock: Mock<CatalogService>

beforeEach(() => {
  catalogServiceMock = mock<CatalogService>()
  catalogServiceMock.fetchProducts.mockResolvedValue(
    new RestResponse({ body: [ProductFaker.fake()] }),
  )
})
~~~

This keeps tests aligned with typed contracts and makes the expected dependency calls explicit.

### Hooks

- Do not mock the hook in its own test.
- Mock services, the router, context, storage, and external APIs used by the hook.
- Await asynchronous effects inside `act`.
- Verify final state and calls made to dependencies.

~~~ts
const { result } = renderHook(() => useHomeScreen())

await act(async () => {
  await new Promise((resolve) => setTimeout(resolve, 10))
})

expect(result.current.collections).toEqual(expectedCollections)
expect(catalogServiceMock.fetchProductsByCollection).toHaveBeenCalledWith(collection.id)
~~~

When applicable, the hook should cover loading, success, empty state, error, retry, validation, submission, mutation success, mutation failure, and navigation.

### Views and widgets

- Mock the corresponding hook in the `index.tsx` test.
- Configure the hook return value for each visual state.
- Interact through roles, labels, stable text, or `testID`.
- Verify that the view delegates events to the hook.
- Mock a complex child only when the view test does not need to validate that child's behavior; the child must have its own test.

Example:

~~~ts
jest.mock("../use-home-screen", () => ({
  useHomeScreen: jest.fn(),
}))

const useHomeScreenMock = jest.mocked(useHomeScreen)

useHomeScreenMock.mockReturnValue({
  isLoading: true,
  // remaining hook contract
})
~~~

Do not broadly mock every component on a screen if that prevents validation of relevant visual composition.

### What may be mocked

- core service interfaces;
- `useRestContext` and other composition contexts;
- `expo-router` and navigation;
- storage, linking, animations, and native modules that are unstable in Jest;
- clocks, timers, and randomness when a scenario depends on them;
- complex child components in isolation tests;
- external network calls in Jest tests.

### What should not be mocked without a clear reason

- the hook in its own test;
- the view in its own test;
- the unit whose rule is being validated;
- the Yampi API in Maestro tests that validate BFF integration; use the local mock server;
- every child of a screen, because this turns the test into an implementation test without composition.

Use `jest.clearAllMocks()` in `beforeEach` and explicitly configure each dependency's return value for every relevant scenario.

## 6. Hook test patterns

Use `renderHook` from `@testing-library/react-native`.

Recommended structure:

~~~ts
describe("useCatalogScreen", () => {
  beforeEach(() => {
    jest.clearAllMocks()
    // configure services and context
  })

  it("should expose products after a successful request", async () => {
    // configure response
    const { result } = renderHook(() => useCatalogScreen())

    await act(async () => {
      // wait for the effect
    })

    expect(result.current.products).toEqual(expectedProducts)
  })
})
~~~

Test observable behavior, not the internal order of `useEffect` details. For asynchronous calls, configure resolved, rejected, and pending responses according to the state being tested.

## 7. Widget and screen test patterns

Use `render`, `screen`, and `fireEvent` from `@testing-library/react-native`.

Selector priority:

1. `getByRole` with an accessible name;
2. `getByLabelText` for fields;
3. `getByTestId` for dynamic elements or elements without stable text;
4. `getByText` for content that is genuinely visible to the user.

Prefer behavior over snapshots. A test should answer what the user sees and does:

- loading is displayed;
- error and retry are displayed;
- empty state is communicated;
- loaded content is rendered;
- fields accept input;
- buttons delegate actions;
- navigation occurs with the correct parameters;
- controls are disabled at their limits.

Every interactive element must have an accessible name or stable `testID`. For Maestro, `testID` should follow the `<component>-<action/type>` format; examples: `home-search-input` and `home-newsletter-submit`.

## 8. Controller and API Route patterns

### Controller unit tests

Mock the service interface and provide a controlled `Http`. Verify that the controller:

- reads the correct parameters;
- calls the service with the expected contract;
- forwards the `RestResponse` to `http.send`;
- preserves success and error responses.

### API Route tests

Test the exported function (`GET`, `POST`, etc.) with a realistic `Request` and route context. Cover:

- successful response and status;
- body, query, and route parameters;
- query-string transformations, including arrays;
- invalid payload with status `422`;
- `AppError` with its status;
- unexpected errors with status `500`.

Do not duplicate every `ExpoRoute` detail in each route test. Keep route-specific cases in the route suite and maintain a separate suite for the `ExpoRoute` adapter.

For real HTTP integration, run Expo and the Yampi mock server. This suite verifies the chain:

~~~text
Request -> Expo API Route -> Controller -> Yampi Service -> Yampi Mock
~~~

## 9. Yampi mock server

The local server lives in `tests/mocks/yampi-mock` and is started with:

~~~bash
npm run mock:yampi
~~~

Configure the BFF to point to it:

~~~env
YAMPI_API_URL=http://127.0.0.1:4010
YAMPI_SECRET_KEY=mock-secret
YAMPI_USER_TOKEN=mock-token
~~~

Use deterministic fixtures and explicit scenarios. To reset or change a scenario:

~~~text
GET  /__test/health
POST /__test/reset
POST /__test/scenario
~~~

The mock server must:

- respond only to endpoints required by the tests;
- simulate success, empty, and failure states deterministically;
- never depend on the external Yampi API;
- use dedicated external fakers when responses contain many fields;
- allow reset between scenarios.

The mock server must not be imported by hook unit tests. It is an integration/E2E dependency.

## 10. Maestro patterns

Each flow must validate a functional journey, not internal React details.

Minimum structure:

~~~yaml
appId: br.com.sertton.sertton
---
- launchApp
- extendedWaitUntil:
    visible:
      id: "home-search-input"
    timeout: 90000
- tapOn:
    id: "home-search-input"
~~~

Rules:

- use an `appId` compatible with `app.json`;
- wait for a stable element before the first interaction;
- prefer `testID` for dynamic elements and text for stable user-facing content;
- use `scrollUntilVisible` for content outside the viewport;
- validate the final result, not only the tap;
- cover success, empty, validation, and relevant failure states in critical journeys;
- keep each flow independent and repeatable;
- never depend on the real API;
- avoid fixed `sleep`; prefer automatic waiting and `extendedWaitUntil`;
- use `killApp`/`launchApp` or the local deep link according to the test infrastructure;
- use `openLink` with the Expo scheme registered for the app, which is `sertton://` in this project.

Maestro files are YAML. The `.maestro` extension is not mandatory and is not used in this project.

## 11. Execution

### Jest tests

~~~bash
npm test -- --runInBand
npm run check:types
npm run check:code
~~~

For coverage:

~~~bash
npm run test:coverage
~~~

### Maestro

The project runner executes only `tests/screens`:

~~~bash
npm run test:integration
~~~

The `scripts/run-maestro-tests.mjs` script removes `maestro-output` before and after execution, including when the run fails. This directory is temporary and must not be committed.

To run one flow manually:

~~~bash
maestro test tests/screens/home/home-content.yaml
~~~

### Recommended order

1. run the affected unit/widget test;
2. run `npm test -- --runInBand`;
3. run `npm run check:types`;
4. start the Yampi mock when the flow depends on the API;
5. run the affected Maestro flow;
6. run the complete Maestro suite before delivery.

## 12. Functional coverage criteria

For each feature, identify its observable transitions:

| Area | Minimum cases |
| --- | --- |
| Loading | loading, success, empty, and error |
| Interaction | valid input, invalid input, and limits |
| Mutation | submission, disabled state during submission, success, and failure |
| Navigation | correct destination and parameters |
| API | success, validation, domain error, and unexpected error |
| E2E | critical journey, empty scenario, and relevant failure scenario |

Do not pursue an isolated percentage target. The goal is to cover decisions and states that change user-visible behavior.

## 13. Anti-patterns

- testing screens only through snapshots;
- testing the real hook inside the view test and duplicating its suite;
- mocking the hook in its own test;
- using large manual objects when a faker exists;
- using uncontrolled random data without a seed or without controlling the relevant property;
- asserting implementation details instead of observable behavior;
- using the real Yampi API in automated tests;
- placing Maestro flows with mocks or scripts;
- committing `maestro-output`;
- using long fixed waits to hide synchronization problems;
- creating E2E tests for every variation of a rule that can be covered by a unit test.
